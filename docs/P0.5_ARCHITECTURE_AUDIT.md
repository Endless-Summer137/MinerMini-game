# P0.5 Architecture Readiness Audit

Date: 2026-05-14

## Scope

This audit checks whether the current P0.4 prototype is ready for future P1/P2 extensions without adding new gameplay systems yet.

Preserved P0.4 behavior:

- secured loose ore scoop behavior
- non-magnetic default scoop
- embedded ground crusher sell point
- load-ratio based unload timing
- reverse movement behavior
- mobile-first pointer/joystick control

Explicitly not added:

- levels, endless mode, base camp, merchants, workers, cart cargo, warehouses, monetization, ads, formal art, or new playable ore types

## Summary

The prototype is still a single-file canvas P0, but the core extension seams are now explicit enough for P1 planning. The light refactor added data tables for ore, blade, vehicle chassis, vehicle skin, crusher type, and upgrade definitions while keeping the current playable values unchanged.

## Ore Type Data

Status: partially ready after P0.5 refactor.

`ORE_TYPES.basicOre` now owns:

- `id`
- `displayName`
- `radius`
- `mass`
- `pushResistance`
- `requiredPush`
- `saturationPush`
- `maxPushSpeed`
- `scoopFriction`
- `capacityCost`
- `baseCoins`
- `baseSpecialCurrency`
- visual colors and particle colors
- `tags`

Current P0 still spawns only `basicOre`. New ore types should be added as data only when gameplay design asks for them.

## Secured Ore Identity

Status: ready for future ore identity.

Each mineral object keeps its `type` reference through `looseOre`, `captureCandidate`, `securedOre`, and `deliveredOre`. Securing ore does not convert it into a generic inventory item.

Future ore-specific capacity, payout, visual, and tag behavior can read from `mineral.type`.

## Capacity Calculation

Status: ready for capacity-cost extension.

Current P0 still behaves as one ore equals one capacity unit because `basicOre.capacityCost = 1`.

The secured load display and capture capacity now use capacity units. Future ore can use:

- normal ore: `capacityCost = 1`
- heavy ore: `capacityCost = 2`
- rare ore: `capacityCost = 3`

Future cart cargo should extend the load source rather than replace the scoop state:

```text
currentLoad = scoopOreCapacityUsed + cartOreCapacityUsed
maxLoad = scoopCapacity + cartCapacity
```

## Crusher Reward Rules

Status: ready for data-driven payout rules.

`CRUSHER_TYPES.embeddedGroundCrusher` now owns crusher reward multipliers, and `calculateCrusherPayout` calculates rewards from ore type data plus crusher type data.

Current P0 output is unchanged because:

- `basicOre.baseCoins = 1`
- `basicOre.baseSpecialCurrency = 0`
- crusher multipliers are `1`

Future examples can fit this shape without adding merchants now:

```text
basicOre.baseCoins * crusher coinMultiplier
basicOre.baseSpecialCurrency * crusher specialCurrencyMultiplier
```

Special currency is calculated but not displayed or spent in P0.

## Blade Type Independence

Status: improved, still P0-single-active-blade.

`BLADE_TYPES.scoopBlade` now owns:

- shape
- width
- length
- capacity
- capture rules
- lip collision tuning
- special assist hooks
- allowed ore tags

The active blade is still the default scoop. Future magnetic, push, or drill blades should be added beside `scoopBlade` instead of changing vehicle movement.

Remaining P0-only coupling:

- most blade collision logic still lives in shared functions
- there is no runtime blade switching yet
- allowed ore tags are present but not enforced yet

## Vehicle Chassis, Skin, And Blade

Status: clearer separation.

`VEHICLE_CHASSIS.prototypeHauler` owns movement and collision body data:

- speed
- body radius
- wall footprint radius
- reverse threshold
- reverse speed multiplier

`VEHICLE_SKINS.orangePrototype` owns visual colors only.

`BLADE_TYPES.scoopBlade` owns scoop mechanics.

This means future changes should follow these boundaries:

- chassis changes movement/handling/body collision
- skin changes visuals only
- blade changes scoop/mining mechanics
- crusher type changes payout/processing rules

## Upgrade Data

Status: centralized for current P0 upgrade.

`UPGRADE_DEFS.pushPower` now owns:

- id
- display name
- cost
- push force multiplier
- blade width bonus
- placeholder capacity/crusher/reward effects

Current P0 still supports only the one push upgrade. Future upgrades can add more effects without scattering new constants through the gameplay loop, but a real upgrade inventory/system does not exist yet.

## Hardcoded Assumptions Still Present

These are acceptable for P0.5 but should be revisited before a larger P1/P2 content expansion:

- only one active ore type is spawned
- only one active blade type is selected
- only one active chassis and skin are selected
- only one crusher exists in the world
- special currency is calculated but not surfaced
- upgrade state is still a single boolean
- the prototype is still a single `main.js` file
- there is no automated browser regression suite yet

## Recommendation Before P1

The code is ready for small P1 experiments as long as new systems continue to enter through the data tables first. Before adding many ore types, blade types, or upgrades, consider splitting `main.js` into modules for data, state, physics, rendering, and input.
